## Report A: Real-Time Edge Video Streaming & Control (Computer Networks)

### References

1. **Schulzrinne, H., Casner, S., Frederick, R., & Jacobson, V. (2003).** *RTP: A Transport Protocol for Real-Time Applications*. IETF RFC 3550.
   - *Why it matters*: Provides packet framing, sequence numbering, RTCP Receiver Reports (RR) for QoS tracking, and the APP packet specification used to deliver AI results.
   - *Supports Section*: Network Transport Architecture & Control Protocol.

2. **Schulzrinne, H., & Casner, S. (2003).** *RTP Profile for Audio and Video Conferences with Minimal Control*. IETF RFC 3551.
   - *Why it matters*: Establishes standard payload type mappings and specifies the standard 90 kHz reference clock for video streams.
   - *Supports Section*: Stream Clocking & Session Configuration.

3. **Berc, L., Fenner, W., Frederick, R., & McCanne, S. (1998).** *RTP Payload Format for JPEG-compressed Video*. IETF RFC 2435.
   - *Why it matters*: Defines fragmentation, JPEG headers, and restart markers for encapsulating low-latency MJPEG video over RTP.
   - *Supports Section*: Video Ingestion & Packet Encapsulation.

4. **Ott, J., Wenger, S., Sato, N., Burmeister, C., & Rey, J. (2006).** *Extended RTP Profile for Real-time Transport Control Protocol (RTCP)-Based Feedback (RTP/AVPF)*. IETF RFC 4585.
   - *Why it matters*: Permits immediate or early transmission of RTCP feedback, enabling rapid rate-adaptation cycles.
   - *Supports Section*: Low-Latency Feedback & AIMD Rate Adaptation.

5. **Johansson, I., & Sarker, Z. (2017).** *Self-Clocked Rate Adaptation for Multimedia (SCReAM) in Mobile WebRTC*. IETF RFC 8298.
   - *Why it matters*: Serves as a reference design for delay- and loss-sensitive media adaptation when designing the AIMD controller.
   - *Supports Section*: Congestion Control & Bitrate Adaptation.

6. **Friedman, T., Caceres, R., & Clark, A. (2003).** *RTP Control Protocol Extended Reports (RTCP XR)*. IETF RFC 3611.
   - *Why it matters*: Defines extended metrics including burst/gap loss models and round-trip delay estimates.
   - *Supports Section*: Network Observability & Diagnostic Metrics.

7. **Gilbert, E. N. (1960).** *Capacity of a burst-noise channel*. *Bell System Technical Journal*, 39(5), 1253–1265.
   - *Why it matters*: Introduces the 2-state Markov chain for modeling bursty channel dropouts.
   - *Supports Section*: Channel Error Modeling & Emulation.

8. **Elliott, E. O. (1963).** *Estimates of error rates for codes on burst-noise channels*. *Bell System Technical Journal*, 42(5), 1977–1997.
   - *Why it matters*: Extends the Gilbert model by allowing non-zero error probabilities in the good state, forming the Gilbert-Elliott model.
   - *Supports Section*: Burst Loss Simulation.

9. **Hemminger, S. (2005).** *Network Emulation with NetEm*. In *Proceedings of the Linux Conf AU*, Canberra, Australia.
   - *Why it matters*: Defines the Linux traffic control (`tc qdisc netem`) interface used to inject controlled delay, jitter, and loss on the Pi 5 interface.
   - *Supports Section*: Testbed Emulation Methodology.

10. **ns-3 Consortium (2024).** *ns-3 Network Simulator: Point-to-Point and Error Models Documentation*. ns-3 Project.
    - *Why it matters*: Documents the `RateErrorModel` and `BurstErrorModel` implementations used to validate Bernoulli and Gilbert-Elliott regimes.
    - *Supports Section*: Simulation Methodology & Validation.

### Key Facts with Exact Sources

- **RTP QoS Guarantees**: RTP provides no mechanisms for timely delivery or QoS guarantees; reliability must be handled by lower layers or upper-layer adaptation (RFC 3550, §1).
- **RTCP Bandwidth Rule**: RTCP traffic is restricted to 5% of overall session bandwidth; 1.25% is allocated to senders and 3.75% to receivers (RFC 3550, §6.2).
- **Interarrival Jitter Filter**: Jitter $J$ is calculated from arrival times $R$ and transit times $S$ as $D(i,j) = (R_j - S_j) - (R_i - S_i)$ and updated recursively:
  $$J(i) = J(i-1) + \frac{|D(i-1, i)| - J(i-1)}{16}$$
  (RFC 3550, §6.4.4 & Appendix A.8).
- **Sender-Clock Round-Trip Latency (RTT)**: Calculated at the sender upon receiving an RR without synchronized clocks using reception time $A$, Last SR timestamp ($LSR$), and Delay Since Last SR ($DLSR$):
  $$RTT = A - LSR - DLSR$$
  (RFC 3550, §6.4.1).
- **RTCP APP Packet Format**: Identified by payload type 204 with a 5-bit subtype, a 4-byte ASCII name identifier, and arbitrary application data (RFC 3550, §6.7).
- **MJPEG Clock Rate**: The RTP timestamp clock frequency for MJPEG payload format is fixed at 90,000 Hz (RFC 3551, §5; RFC 2435, §3).

### Key Facts with Exact Sources

- **Age of Information (AoI) Definition**: Given generation time $U(t)$ of the newest received update at time $t$, instantaneous AoI is defined as:
  $$\Delta(t) = t - U(t)$$
  (Kaul et al., 2012, §II).
- **Latest-Value vs. FIFO Queuing**: Standard FIFO buffering causes packet queuing delay that grows under heavy load, severely degrading AoI; dropping stale samples (zero-wait / latest-value policy) minimizes average AoI (Kaul et al., 2012, §IV; Yates et al., 2021, §III).
- **POSIX `SCHED_FIFO` Execution**: Under `SCHED_FIFO`, the running thread runs indefinitely until it blocks on I/O, yields via `sched_yield()`, or is preempted by a strictly higher-priority real-time thread; it has no timeslice (IEEE Std 1003.1, §sched; Linux `sched(7)`).
- **FreeRTOS Priority Preemption**: The scheduler guarantees the highest-priority Ready-state task executes immediately; tasks of equal priority timeslice if `configUSE_TIME_SLICING` is enabled, while ISRs preempt via `portYIELD_FROM_ISR()` (Mastering FreeRTOS, §3.1).
- **libcamera Monotonic Timestamps**: Hardware frame acquisition timestamps exposed via `Request::metadata()` and `FrameMetadata::timestamp` are captured in nanoseconds from `CLOCK_MONOTONIC`, eliminating NTP/wall-clock drift (libcamera Architecture Guide, §Frame Analysis).
- **Priority Inversion Avoidance**: Unbounded priority inversion across shared resources (e.g., UART mutexes) is bounded using priority inheritance, wherein a lower-priority task holding a mutex temporarily runs at the priority of the highest-priority pending task (Sha et al., 1990, §III; FreeRTOS `configUSE_MUTEXES`).
